上周三半夜，我的批处理脚本突然全红，一片 429。第一反应是改代码，改了两版都没用，气得我直接关机睡觉。第二天早上冷静下来把响应头翻出来一看，`Retry-After` 白纸黑字写着呢——是我自己没看。后来把三个高频错误码的排查思路整理成清单，再遇到就不慌了，分享出来。

### 一、429 Too Many Requests：你太快了

高频病因就三类：循环里裸调 API 没加间隔；多进程共用一把 Key，频率累加超限；重试风暴——失败后立刻重试，越试越限，恶性循环。

处理思路：先看响应头里的限流信息（常见 `Retry-After`、`X-RateLimit-Remaining`），有等待时间就照做。没给的话，用指数退避加抖动：

```python
import time, random

def call_with_backoff(fn, max_retries=5):
    for i in range(max_retries):
        resp = fn()
        if resp.status_code != 429:
            return resp
        wait = min(2 ** i + random.random(), 60)   # 退避上限 60 秒
        time.sleep(wait)
    raise RuntimeError("重试次数用尽，先查限流策略")
```

### 二、401 Unauthorized：你是谁

401 我遇到的头号原因是复制 Key 时带了换行或空格，听着弱智，但真的一年能碰上三次。其他常见病因：`Authorization: Bearer` 后面少了空格；环境变量没加载（本机有值、服务器上没配）；Key 已过期或被吊销。

处理有个小技巧：先打印长度而不是内容（`print(len(api_key))`），长度不对八成是复制出了问题——直接打印内容的话，万一又贴进日志，那就是二次泄露。然后核对 Header 格式，最后去控制台确认 Key 状态。记住一点：401 重试没有意义，修配置才是正道。

### 三、403 Forbidden：我知道你是谁，但你不能进

病因：子 Key 权限范围不够；目标模型没开通或不在白名单；账号触发风控；来源地区被服务端拒绝。

和 401 的区别要记牢：401 是「没验明身份」，403 是「验明了，但不给」。前者去修密钥，后者去控制台改权限和开通状态——这类问题改代码没用。

### 四、三条教训

只对 429（以及偶发的 5xx、网络超时）做自动重试。对 401/403 重试，是对限流与风控策略的二次挑衅。退避一定要加上限和抖动，不然几百个任务同时醒来，就演变成新的重试风暴。最后一条是心态：限流是产品能力不是故障，尊重 `Retry-After`，比「狂试到成功」体面得多。

报错码不是敌人，是说明书。429/401/403 三个高频错误各有明确病因，按清单排查比盲改代码快十倍。

### 一、429 Too Many Requests：你太快了

**高频病因**：循环里裸调 API 没加间隔；多进程共用一把 Key 频率累加超限；重试风暴——失败后立刻重试，越试越限。

**处理**：先看响应头里的限流信息（常见 `Retry-After`、`X-RateLimit-Remaining`），服务器给了等待时间就照做；没给就用指数退避加抖动：

```python
import time, random

def call_with_backoff(fn, max_retries=5):
    for i in range(max_retries):
        resp = fn()
        if resp.status_code != 429:
            return resp
        wait = min(2 ** i + random.random(), 60)   # 退避上限 60 秒
        time.sleep(wait)
    raise RuntimeError("重试次数用尽，先查限流策略")
```

### 二、401 Unauthorized：你是谁

**高频病因**：Key 复制时带了换行或空格；`Authorization: Bearer` 后面少了空格；环境变量没加载（本机有值、服务器上没配）；Key 已过期或被吊销。

**处理**：先打印长度而不是内容（`print(len(api_key))`），长度不对八成是复制出了问题；再核对 Header 格式；最后去控制台确认 Key 状态。401 重试没有意义，修配置才是正道。

### 三、403 Forbidden：我知道你是谁，但你不能进

**高频病因**：子 Key 权限范围不够；目标模型没开通或不在白名单；账号触发风控；来源地区被服务端拒绝。和 401 的区别要记牢：401 是「没验明身份」，403 是「验明了，但不给」。

**处理**：逐项核对权限和开通状态。这类问题改代码没用，要去控制台改配置。

### 四、避坑

1. 只对 429（以及偶发的 5xx、网络超时）做自动重试。对 401/403 重试，是对限流与风控策略的二次挑衅。
2. 退避一定要加上限和抖动，否则几百个任务同时醒来就演变成新的重试风暴。
3. 限流是产品能力不是故障。尊重 `Retry-After`，比「狂试到成功」体面得多。

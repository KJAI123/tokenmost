# TokenMost 网站迭代规则

**目标：让用户找到可领取的权益，看清额度、领取条件和可信来源。** 采集记录、公开权益和核验是三件事，分别记录。

## 1. 每轮先查缺口

- 跑 `python3 tools/source_audit.py` 留下基线。按「已有稳定信源但未成条」「已上架但待复核」「已有条目但缺少独立证据」依次处理。优先覆盖常设免费 API、每日或每月刷新、即将截止的活动和用户点名的平台。
- 待看线索从 `data-research/discovery-queue.md`、`source_candidates.json`、公众号/RSS 产出和 `review-queue.md` 取。新平台先查 `deals.json`、`sites.json`、`tools/harvest_sources.json` 与 `tools/sources.json`，确认缺的是采集、公开目录、具体权益，还是仅缺证据。
- 每日先处理活动截止、页面变更和高频失联；每周检查各类别是否只依赖单一聚合站，从候选库复核一批高价值缺口。同一域可以有不同产品，但一个 URL 返回 200 不代表内容有效。采集遵守站点规则；遇登录墙、地区限制或页壳，记录所欠证据。

## 2. 用证据决定如何收录

| 证据 | 去向 | 上架条件 |
|---|---|---|
| 官方定价、活动条款、公开文档、可复现的结构化接口 | `deals.json` + `tools/sources.json` | 原文能支持文案中的额度、适用对象与计费条件。 |
| 可复现的实测、公开到账记录 | 佐证，附平台官方入口 | 区分官方条款与实测，注明日期、地区和账号条件；单次结果不能推广成普遍规则。 |
| 公众号、社区、聚合目录或旧快照 | `harvest_sources.json` 或发现队列 | 用于发现；暂无法核实时保持草稿或待复核状态，不写成已核验。 |
| 只剩历史促销、过期、证据矛盾、重复 | 保留处理记录 | 活动过期标 `expired`；信息被证伪或合并时归档并注明理由。 |

每个新公开条目写明：提供方与产品、额度原单位、刷新周期、是否需注册/绑卡/付费/审核、地区与适用对象、截止时间（含时区如有）、公开入口和核验日期。能确认到什么程度就写到什么程度。没有官方比例及依据时，不用 Neurons、积分、次数、CPU/GPU 小时或钱数硬算 Token；每日/每月刷新用 `cadence` 表达，同一权益不因多一条信源而加进总额两次。英文页面的新条目补 `value_en`、`rule_en` 与需要的 `notes_en`。

额度数据使用 `token_quota[]` 保存 `amount`、`unit`、`period`（once/daily/monthly/weekly）。金额有明确模型抵扣用途时，可按已核验官方 DeepSeek 基准显示「购买力参考」，同时保留原金额，不写成实际到账 Token。积分仅在有官方公式时填写 `tokens_per_unit`，注明模型、缓存、输入输出比例和时段；未知比例保留原单位。用户要求估计时，可另外使用 `daily_estimate` 显示可调整的「情景估计」：次数按每次输入输出用量推算，积分可按公开售价估购买力或明确写出的站内假设推算。必须展示区间、假设、原始日额、整理日期；不得把假设写进官方 `tokens_per_unit` 或已核验额度。短期体验用 `quota_days` 限制，日刷新最多按 30 天且不超过剩余活动天数，月额度计一次。`quota_paid`、`quota_upper_bound`、`quota_conditional` 分别标记付费、随机上限和额外资格，不进入常规免费总账。旧估算保存在 `quota_history` 供追溯。新估计使用 `quota_estimates[]` 按 `quota_index` 分别引用一次性、日、周或月额度；旧 `daily_estimate` 继续兼容。一次性与月额分别计一次，日额最多30天，周额按有效天数÷7；不同周期不能全部乘30。原始额度和情景分开存储；同池多个模型或多个视图按 `pool`、`priority` 去重，已换算的原始 Token 不再另估。情景估计可参与列表参考排序，但独立汇总，不自动加入已核验总账或 API 抵扣。音频/生图/算力不能套文本积分情景。

前端 `assets/token-math.js` 与静态页 `tools/token_math.py` 使用同一数据；发布前运行 `node tools/test_token_math.js` 检查官方公式、币种、周期、有效期、重复计数及全部条目的两端一致性。比价器每日用量乘 30 得月费用，只有适用目标模型且已核验的 API 原始额度能抵扣费用；不能拿 DS 购买力当原模型实际余额，也不能拿免费轻量模型抵扣同厂旗舰。

有官方积分扣费表时，`quota_estimates.method=model_rates` 按每千 Token 的输入/输出价格提供三种替代模型情景，默认假设无缓存、输入:输出=3:1；三个模型共用一份积分，不能相加。有官方美元输入单价时可用 `model_budget` 展示「仅输入预算」，对应金额必须 `convert:false`，避免同笔余额同时计入 DS 购买力；不凭免费输出推测无限输出量。`starts_after_days` 限制首月计算窗口，注册满一个月才发的月赠用 30 表示首月排除；原文的日历月发放规则仍保留在说明中，不把延迟月赠和注册送额一起计入首月。公开套餐均价只是购买力代理，必须注明套餐含其他权益，不称作独立积分售价。搜索缓存中的旧数字不能替代本轮实时条款。

`url` 是用户的操作入口；`sources` 是证据数组，每项至少 `url` 与 `title`，新条目再标 `kind`（`official` / `firsthand` / `community` / `aggregator`）。可用的补充链接全部留在原条目；同一权益按平台、产品、领取门槛、额度和周期核对后合并，共享同一 `id`，不要按域名粗暴去重。合并时在旧条目保留证据和指向，并把独有证据并入主条目。URL 失效或被替换时，保留原来源作为历史证据，并补上新 URL 和处理说明。

## 3. 采集、核验与同步

- `tools/harvest_sources.json` 发现增量，`tools/sources.json` 监控已知权益，`sites.json` 提供平台入口。一个来源已存在就更新关键词或绑定，不再造重复采集任务。每个采集登记使用独立 ID；工具从 URL 生成 ID，不能只取 docs、console 等常见子域名。
- 新增官方页面监控默认使用 `auto_verify: false`。哈希一致表示页面未检测到变化，不代表到账实测，也不更新人工核验时间；发生持续变更则进复核。已有自动续期规则，逐条确认来源能证实权益再保留。监控无法直接证实付费状态或到账时，禁止跨过人工复核。
- 同步只修改负责的字段。手工维护的 `sources`、领取规则和地区/到账限制按条目 ID 合并；不能用旧快照或空数组覆盖。自动同步在写回前检查已有证据链接是否丢失，拦下回归并输出条目 ID。GitHub Pages 的推送发布也与推送前的版本比较；独立采集任务写入前同样跑基线对比。
- 发布前用 `git show HEAD:deals.json > /tmp/tokenmost-before.json` 取基线，再跑 `python3 tools/source_audit.py --against /tmp/tokenmost-before.json` 和 `python3 tools/check.py`。检查新增条目、归档原因、RSS/平台页/搜索入口变化；区分「已核验」「待复核」「监控中」。线上发布前只合入目标变更，先确认最新自动同步和可回滚版本。

## 4. UI 验收与记录

- 每轮选一个明确问题（如找不到某平台或不清楚领取门槛），记下当前完成路径，再比较改版后的点击数、步骤和失败点。
- 首页保持列表紧凑。摘要默认可见，聚合和单条均可打开原始信源。折扣链接直接打开领取页，独立折扣码提供复制入口。门槛和过期状态应在列表中可见。
- 用户点名的高价值付费补贴可放在默认首页首屏的独立「补贴推荐 · 付费」区；与免费额度排序、免费筛选和总账分开。必须有当前官方依据、价格/模型用量上限与推荐截止日。`featured_until`只控制推荐位，不能当成整个订阅停服日；过期或变为待复核即撤推荐，不用虚增Token数换取排序位置。
- 需要企业资质、项目审核或开源维护者资格的条目列入首页底部的申请制权益，额度以原单位展示。首页首月总账仅汇总可按当前常规领取条件估算的额度。
- 首页「收录首月情景」可展示更广的收录规模，但必须同时列出已核验、待复核、日额度估计三项，使用约数并注明含待复核。范围随估计参数变化，不称作保证到账量或可抵扣余额。总账提供逐项金额、状态与原单位；原已核验总账、API抵扣和预算计算保持严格口径。不限量、未定额或音视频/工具/算力等不适合折算的权益另列数量与明细，不能填零或虚造Token数。查出旧模型下线、赠额取消或计费体系替换时，先更新记录，不能为扩大总数继续累加历史权益。
- 中英文首页分别验证手机（至少 320px 和常用手机尺寸）、平板和桌面：列表直接显示全部匹配平台，无横向溢出；搜索、空状态重置、筛选、排序、信源展开、核验日期和总账可用。键盘能访问主要入口，焦点可见；不强制播放动画。
- 每轮写清修改目的、核验日期与来源、新增/更正/归档数量、未解决线索、实际验证范围。线上检查以生产域真实返回为准，和本地预览分开记录。
- 首页沿用 Open Design「TokenMost 青墨工作台重构」的三原色版本。蓝色用于导航与普通领取，亮黄色用于折扣领取，红色用于截止或失效，绿色用于已核验。中英文共用样式维护在 `assets/workbench.css`。每轮检查 1440×900 桌面首屏至少完整显示 4 条情报，320px 窄屏的群二维码可直接看见并能点击放大。先读平台与简述，再看额度、核验和领取操作。

- Logo 优先使用当前官方产品/品牌素材并保存本地来源记录；按提供方名称覆盖邀请链、文档域名，资讯站与CDN域名不能冒充品牌。灰底字母图片即使能解码也不算Logo；已识别占位图的哈希列入校验，不能重新引用。加载成功前保留文字标识，失败时回退；无法访问的老站不造品牌图。多机构目录可使用明确标记的分类图标。

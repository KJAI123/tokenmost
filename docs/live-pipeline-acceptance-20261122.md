# 采集、通知与镜像发布实测（2026-11-22）

本轮依据用户授权进行真实网页采集与飞书通知测试。生产源站已含 `6fba53c` 三类修复，当前业务基线为自动同步提交 `50612ab`；后续发布保留该基线数据。

生产全量快照记录 186 个源：176 个 `ok`、6 个 `error`、2 个停用、2 个遵守 robots 限制。另在香港源站用实际部署的采集代码重新抓取 Jules、LongCat、ZCode 更新日志、火山方舟协作计划、TRAE 国际站，分别命中 0、1、4、30、12 处。Jules 的零命中保留为人工复核线索，不能把可访问页面等同于已核验权益。五个定向结果写入网站目录外的私有验收目录，原 `latest.json` 与 `prev.json` 哈希不变；合并到私有全量副本进行真实差异检查，源数保持 186、没有虚假的移除源。

服务器默认 `python3` 是 3.6.8，不能运行声明支持 Python 3.9+ 的脚本；实测使用现有 `/usr/bin/python3.11`（3.11.13）。未更改系统默认解释器。既有 GitHub 采集工作流使用 Python 3.12。

飞书使用既有唯一启用的 DM 目标和正式通知模块：先发送一条带唯一测试标识的消息，回读确认送达后，使用相同内容与同一 `uuid` 做一次受控重复请求。两次响应均成功且返回同一消息 ID；消息详情、完整会话历史和飞书客户端搜索均只找到一条测试消息。没有恢复心跳通知或新增定时推送。该结果验证本次相同标识的短时间重复请求，不是跨任意时间和不同内容的绝对去重承诺；结果不确定仍按退出码 3 要求人工核对，禁止自动重发。

发布核对发现主站已更新，而 GitHub Pages 镜像仍停留在上一轮人工推送。原因是 [GitHub 官方说明的 GITHUB_TOKEN 触发限制](https://docs.github.com/en/actions/concepts/security/github_token)：自动同步用该令牌推送时，不会再触发 `push` 发布流程。现有 Pages 工作流补充 [workflow_run 完成事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)，仅接受本仓库 `main` 的 `daily-sync` 成功完成后部署；获取最新 main，并用采集起始提交做证据回归基线。原定时采集频率和令牌权限未变，保留现有发布并发控制、换算检查与信源保全门禁。

六个失败源仍需后续按证据处理：IBM API Keys 登录墙（401）、移动云断连、MiniMax 国际站重定向异常（307）、DeepInfra 旧定价页（404）、GLM Coding 社区仓库（404）、京东云访问限制（493）。本轮不凭失败响应更新权益，不绕过登录或站点限制。

发布前换算/时钟边界/JS-Python 一致性检查、20 项管线离线回归与来源保全通过。真实通知凭证和原始采集验收日志留在本机与源站私有输出目录，不进入站点发布包。
